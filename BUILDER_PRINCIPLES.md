# Builder Principles v0.1

## 1. Build real things

A project should have a clear user outcome and a testable end-to-end flow. A polished README is not a substitute for a working system.

## 2. Official-first, evidence-first

Arc-specific claims must be checked against current authoritative sources before they become implementation rules.

## 3. Smallest useful MVP

Prefer a narrow, working flow over a wide unfinished feature set. Expand only after the core path is verified.

## 4. Verify the result

For blockchain work, distinguish between a request being sent, a transaction being mined, and the intended state change being verified.

## 5. Preserve safety boundaries

Never put credentials, private keys, API keys, or other secrets into source control or documentation.

## 6. Learn from failure

A failure is useful when we can explain the cause, the fix, and how to prevent recurrence.

## 7. Reuse knowledge

If a solution is likely to apply to another project, extract it into a template, workflow, lesson, or troubleshooting entry.

## 8. Keep provenance

When knowledge comes from a source, keep enough context to identify the source and its date/version when relevant.

## 9. Do not confuse forks with original work

Official examples and forks are valid learning starting points. Clearly distinguish upstream code from our own changes and original contributions.

## 10. Improve the system after every project

The guide is a living system. A completed project should make the Builder workflow better than it was before the project started.
